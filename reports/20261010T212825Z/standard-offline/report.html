Large offline-first CRDT benchmark

Status: complete; updated 2026-10-10T21:40:48.210117+00:00

267 scenario trials recorded; 267 completed with verified convergence. Planned first-pass trials: 89. Untested combinations remain untested; budget exits are not correctness failures.

Native release Rust and Node on Linux; actual CPU affinity is recorded in metadata (the automated campaign pins one logical CPU). Each init, edit, merge, cold-open and verification stage uses a fresh process. Server and client merges each own exactly one document. Edits use identical procedural ASCII traces. A separate non-CRDT Rope reference computes expected states for each local branch. After two server save/reload boundaries and a client save/reload boundary, both replicas must converge and preserve branch sentinels. Duplicate updates are checked in separate verification processes. Reverse-order delivery is not part of this night campaign.

Merge peak: resident-memory high-water mark reset immediately before importing updates, including update buffers and CRDT work. Editing peaks exclude the checkpoint serialization/loading operation itself; checkpoint peaks remain in raw results. Merge peaks start at already-resident post-load memory; cold-load and later persistence peaks are separately recorded in raw phase results. Linux /proc/self/clear_refs=5 resets VmHWM; support is recorded. The worker exit/kernel peak can be lower after a reset, so all phase peaks are retained. Verification/reference peaks are excluded from merge rankings. Lazy work triggered by merging remains inside merge cost.

Cold open: load raw persisted document, read all text/map values, discard the returned view, perform one middle insertion. The table includes the largest cold-stage peak and final process RSS, not just retained CRDT heap. Native live heap is measured in a separate allocation-instrumented process; JavaScript post-GC heap + ArrayBuffers is approximate and not directly comparable. JavaScript forces GC at load/reload boundaries, outside load timing; total stage wall time includes it.

Disk: smaller of native saved bytes and a lossless Zstd-3 wrapper; cold loads use raw bytes. Loro full operation exports retain all history; no shallow snapshots, CRDT resets or destructive history pruning. Yrs/Yjs GC and wire-format settings are encoded in each variant name (native Yrs defaults to GC and V2, with explicit V1 and no-GC variants). Snapshot-tail variants use an application frame containing a full base snapshot and the incremental tail, without deleting CRDT metadata. Native Automerge tuned variants use 64 KiB initial transactions; the bounded adapter uses compressed native changes imported 32 at a time with causal delivery. Diamond Types is text-only in this harness. All inputs are synthetic ASCII with unique random line IDs; mixed fields are flat scalars. No Flutter bridge, mobile/Web builds, rich text, nested structures, network, database fsync, UI, concurrent-server load or real elapsed month is measured. Inputs differ from the earlier small campaign; compare engines within this campaign. Small timing differences and production tail latency require more samples.

Global budget: 3.494966909752952 h; phase timeout: 120 s; trial budget: 360 s; sampled per-process RSS guard: 12 GiB; host reserves: 4 GiB available RAM and 10 GiB free disk. Guards may overshoot between samples. First pass prioritizes coverage; subsequent passes repeat successful combinations up to 3 trials. Failed configurations are not retried in later passes. Jobs exceeding the wall budget are stopped and recorded. Work files are cleaned after every trial; timings/results/logs remain.
